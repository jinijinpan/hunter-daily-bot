# 识别系统 V2 实施方案

## 1. 背景

当前脚本已经具备每日补给、小秘书任务、多个战斗任务、深渊连续挑战和角色切换等流程，但仍未在真实环境中完整跑通一轮。

现有识别方式主要是：

1. 截取整个微信小游戏窗口。
2. 每帧重新检测游戏内容顶部并缩放到 `1091x700`。
3. 在固定区域进行单张灰度模板匹配。
4. `wait_for_page()` 或 `wait_for_one_of()` 在固定时间内等待指定页面。
5. 使用录制坐标点击控件。

这种方式在静态参考图和模拟状态机测试中表现良好，但容易受到加载延迟、动画、角色和场景变化、窗口缩放、按钮倒计时以及截图标准化抖动影响。

## 2. 真实运行证据

以下记录表明，问题不能继续通过增加整页模板解决：

| 运行记录 | 运行时结果 | 失败截图离线重识别 | 说明 |
| --- | --- | --- | --- |
| `runs/20260727-203905` | 无尽塔 `0.552`，超时 | 同一截图约 `0.927` | 页面可能在超时边界才稳定，或运行时标准化发生瞬态偏移 |
| `runs/20260727-191749` | 小秘书 `0.228`，超时 | 同一截图约 `0.937` | 单帧识别结果和保存后的诊断截图不一致 |
| `runs/20260727-074437` | 深渊胜利页连续点击后超时 | 耗尽页截图约 `0.982` | 预期状态集合、动画和实际稳定页面没有同步 |
| `runs/20260726-194807` | 等待魔物入侵结算超时 | 截图仍是魔物入侵选关页 | 点击没有进入战斗，但程序只等待结算，不验证点击结果 |

现有单元测试大量使用 `FakeGame` 队列，只能证明代码分支能够执行，不能证明真实截图能被正确识别，也不能证明点击在游戏中生效。

## 3. 目标

V2 识别系统应满足：

- 游戏窗口尺寸变化后仍能稳定识别。
- 不因单帧动画或加载画面立即停止。
- 页面状态由多个局部信号共同确认。
- 点击实际检测到的按钮中心，而不是只依赖固定坐标。
- 每次点击后验证动作是否生效。
- 出现预期外但已知的安全页面时能够自动恢复。
- 可以离线回放真实运行截图和录制链路。
- 先跑通单角色，再扩展到三个角色完整循环。

## 4. 非目标

- 不尝试读取微信小游戏 DOM；游戏主要渲染在 Canvas 中，桌面 UI 自动化无法可靠获得内部控件。
- 第一阶段不训练 YOLO 等目标检测模型。
- 不一次性重写所有业务流程。
- 不删除现有模板识别；迁移期间保留为回退信号。

## 5. 总体架构

```text
窗口截图
  -> 稳定视口校准
  -> 标准化画面
  -> 局部检测器集合
       - 页面标题模板/OCR
       - 按钮颜色与轮廓
       - 按钮文字 OCR
       - 数字 OCR
       - 稳定图标模板
       - 弹窗与加载状态
  -> Observation（当前可见事实）
  -> 多信号页面判定
  -> 多帧一致性确认
  -> 工作流状态机
  -> 点击实际控件位置
  -> 动作结果验证
  -> 全局恢复路由
```

### 5.1 稳定视口校准

当前 `DesktopGame.capture()` 每次调用都会重新执行 `_detect_content_top()`。V2 应改为：

1. 启动时连续采集至少 5 帧。
2. 对每帧计算游戏内容顶部候选值。
3. 丢弃明显离群值并取中位数。
4. 缓存窗口客户区尺寸和内容顶部。
5. 只有窗口尺寸发生变化时才重新校准。
6. 将校准结果写入日志和失败诊断 JSON。
7. 如果校准不可信，停止点击并保存原图，不使用随机候选值。

建议新增独立的 `ViewportCalibrator`，避免识别代码直接依赖窗口边框细节。

### 5.2 Observation 数据模型

页面识别不应只返回一个字符串。建议返回可审计的观察结果：

```python
@dataclass
class DetectedControl:
    name: str
    rect: tuple[int, int, int, int]
    confidence: float
    source: str  # template, ocr, color, numeric


@dataclass
class Observation:
    timestamp: float
    viewport: tuple[int, int, int, int]
    title_candidates: dict[str, float]
    controls: list[DetectedControl]
    numeric_values: dict[str, int]
    template_scores: dict[str, float]
    frame_change: float
    state: str
    state_confidence: float
```

所有等待、点击和恢复逻辑都基于 `Observation`，超时时保存观察结果和带框标注图。

### 5.3 局部检测器

优先采用混合方案：OpenCV 局部模板 + 颜色轮廓 + 小区域 OCR。

模板适合：

- 稳定图标。
- 页面标题装饰。
- 关闭、主页、返回等图标。
- 奖励、翻牌等固定结构。

OCR 适合：

- `返回安全区`。
- `再次挑战`、`快速挑战`、`开始挑战`。
- `跳过`、`领取`、`前往`、`确定`。
- 体力、次数和任务进度数字。

建议使用 RapidOCR/ONNX，并且只识别配置中的小范围 ROI，不对整帧持续 OCR。依赖下载应支持中国 PyPI 镜像。

颜色和轮廓适合：

- 金色可操作按钮。
- 蓝色“前往”按钮。
- 灰色禁用按钮。
- 红点、领取提示和确认按钮。

### 5.4 多信号页面判定

页面状态由多个证据组合，不再使用单个模板的最大分数。

示例：

```text
abyss_exhausted:
  (OCR 体力 == 0 OR 检测到“返回安全区”)
  AND 未检测到“再次挑战”

tower_ready:
  标题“无尽塔”
  AND 检测到“快速挑战”或“开始挑战”

tasks:
  标题“小秘书”
  AND “每日任务”标签
  AND 至少一个“领取”或“前往”按钮
```

关键状态至少需要两个独立信号。高风险点击不能仅靠低分 OCR 或单一颜色块触发。

### 5.5 多帧一致性和自适应等待

- 静态页面至少连续 2 帧判定一致后才接受。
- 快速弹窗可使用高置信单帧，但必须限制在当前工作流允许的状态内。
- 使用相邻帧差判断画面是否仍在动画或加载。
- 画面持续变化时延长等待，但设置工作流总上限。
- 只有画面稳定一段时间且仍无法识别时才进入恢复或安全停止。
- 不应在固定 12 秒到期后立刻停止；先做最后一次稳定帧采样。

### 5.6 动作结果验证

点击流程统一为：

1. 检测目标控件矩形。
2. 检查控件属于当前允许动作。
3. 点击矩形中心。
4. 等待原控件消失、下一控件出现或页面进入明显加载状态。
5. 如果未变化，重新聚焦窗口并再次检测控件位置。
6. 有限重试后进入恢复路由，而不是直接等待远端结算页面。

例如魔物入侵点击“快速匹配”后，应先确认已经离开选关页或进入战斗，再等待结算。

### 5.7 全局恢复路由

工作流状态机之外保留一组安全恢复状态：

- 主界面。
- 小秘书。
- 通用奖励弹窗。
- 确认弹窗。
- 翻牌与跳过。
- 返回安全区。
- 主页按钮。
- 已知战斗结算。

遇到预期外页面时先观察 2 至 3 帧，然后交给恢复路由。只有不存在安全动作或置信度不足时才停止。

## 6. 真实回放测试

新增离线回放层，不能只依赖 `FakeGame`：

1. 从 `runs` 和 `recordings` 选择关键真实帧。
2. 统一标准化后保存为压缩 WebP 或优化 PNG。
3. 建立清单文件，记录期望状态、期望控件和禁止动作。
4. 测试视口校准、页面判定、控件位置和状态转换。
5. 对过渡帧明确标记为 `loading` 或 `unknown_transient`，不得误触。

建议结构：

```text
tests/fixtures/recognition/
  manifest.json
  main-role-1.webp
  tasks-role-2.webp
  tower-ready.webp
  abyss-victory.webp
  abyss-exhausted.webp
  monster-stage.webp
```

清单至少包含：

```json
{
  "file": "abyss-exhausted.webp",
  "expected_state": "abyss_exhausted",
  "required_controls": ["return_safe"],
  "forbidden_controls": ["retry"]
}
```

## 7. 观察模式

在允许真实点击前新增观察模式：

- 连续运行 2 至 5 分钟但不点击。
- 输出每帧最终状态、各信号置信度和控件坐标。
- 保存状态变化时的原图、标准化图、标注图和 JSON。
- 允许用户手动操作游戏，脚本只记录识别结果。

观察模式稳定后，再开放单步执行和全自动执行。

## 8. 分阶段实施

### 里程碑 1：稳定截图和真实回放

- 实现视口校准缓存。
- 窗口尺寸变化时重新校准。
- 从现有失败记录建立首批真实回放数据。
- 添加标准化截图回归测试。
- 记录标准化参数和帧差。

验收：同一真实截图在线和离线得到一致的标准化结果与模板分数。

### 里程碑 2：Observation 和局部控件检测

- 实现 `Observation`、`DetectedControl`。
- 实现按钮颜色轮廓检测。
- 接入局部 OCR。
- 实现标题、按钮和数字的组合状态判定。
- 添加观察模式及标注诊断图。

验收：现有真实回放帧能够识别页面和关键按钮，关键页面无高置信误判。

### 里程碑 3：动作验证和恢复路由

- 点击检测到的控件中心。
- 验证点击结果。
- 增加加载/动画检测和自适应等待。
- 实现全局安全恢复路由。
- 超时诊断包含观察 JSON 和标注图。

验收：点击无效时不会直接等待最终结算，也不会在未知过渡帧中连续乱点。

### 里程碑 4：逐流程迁移

按以下顺序迁移：

1. 主界面、小秘书和返回路径。
2. 每日补给和通用奖励。
3. 无尽塔。
4. 深渊挑战。
5. 猎魔战场、魔物入侵。
6. 猎人联赛、无限秘境。
7. 三角色切换与完整编排。

每迁移一个流程，都保留旧实现作为配置回退，直到真实环境通过。

#### 里程碑 4P：测试性能与 GPU OCR 后端

全量测试中的主要高负载来自真实截图 OCR 重复推理和 OpenCV 模板匹配。GPU 优化必须先测量瓶颈，不能假设所有图像处理都能直接转移到显卡。

当前开发机基线：

- GPU：NVIDIA GeForce RTX 3060 Ti，8GB 显存。
- NVIDIA 驱动可用，`nvidia-smi` 报告 CUDA Driver API 13.1。
- 当前 ONNX Runtime 仅有 `CPUExecutionProvider` 和 `AzureExecutionProvider`。
- 当前 `opencv-python` 没有 CUDA 设备支持，模板匹配仍运行在 CPU。
- RapidOCR 配置支持 `det_use_cuda`、`cls_use_cuda`、`rec_use_cuda`，也支持 DirectML。

实施任务：

1. 新增 OCR 性能基准工具，分别记录预热后墙钟时间、进程 CPU 时间、识别结果和实际 ONNX Provider。
2. 将 OCR 后端配置化为 `auto`、`cuda`、`dml`、`cpu`。
3. `auto` 按 `CUDA -> DirectML -> CPU` 的顺序探测，但只有初始化和最小推理自检成功后才启用该后端。
4. 在日志中明确打印实际 Provider；不得仅根据配置宣称正在使用 GPU。
5. CUDA 方案使用 `onnxruntime-gpu`，需要与其要求的 CUDA/cuDNN 运行库匹配。当前机器只有 NVIDIA 驱动，没有发现 `nvcc` 或 cuDNN DLL，因此安装前必须验证依赖方案。
6. DirectML 作为 Windows 上无需单独 CUDA Toolkit 的备选方案，但必须实测速度和识别一致性。
7. GPU 初始化、模型加载或推理失败时自动回退 CPU，并记录一次清晰警告；不能让自动化流程因可选 GPU 后端不可用而停止。
8. 不在同一 Python 环境中无条件同时安装互相冲突的 `onnxruntime`、`onnxruntime-gpu` 和 `onnxruntime-directml`。将 GPU 依赖放入独立可选 requirements 文件或安装脚本。
9. 复用单个 OCR 引擎实例，避免每个测试重新加载模型或重复占用显存。
10. 对回放测试增加按“标准化图哈希 + ROI + OCR 配置 + 模型版本”索引的进程内缓存，避免同一裁剪区域重复推理。
11. 将测试划分为快速测试与完整 OCR 回放测试。开发期默认运行快速测试，里程碑验收和提交前运行完整测试。
12. 保持 OpenCV 模板匹配为 CPU 实现，除非独立基准证明自行维护 CUDA OpenCV 构建有明确收益。第一阶段不编译自定义 OpenCV。

建议配置：

```json
{
  "recognition_v2": {
    "ocr_backend": "auto",
    "ocr_gpu_fallback": true,
    "ocr_cache": true
  }
}
```

验收标准：

- GPU 后端启用时，日志中的实际 Provider 为 `CUDAExecutionProvider` 或 `DmlExecutionProvider`。
- CPU、CUDA/DirectML 对全部回放样本得到相同的状态和关键控件结果。
- GPU 不可用时能够自动回退 CPU，完整测试仍通过。
- 完整 OCR 回放的墙钟时间不劣于 CPU 基线 10% 以上，且进程 CPU 时间有实质下降。
- 快速测试不初始化 OCR GPU 后端，适合频繁开发回归。
- 性能测试结果写入机器可读 JSON，便于后续比较，不能只凭任务管理器主观判断。

这项优化只能将 OCR 推理负载转移到 GPU。模板匹配、图像缩放、颜色轮廓和普通 Python 测试仍会消耗 CPU，因此 OCR 缓存和测试分层与 GPU 后端同等重要。

实施状态（2026-07-28）：后端配置、Provider 实例核验、最小推理自检、GPU
初始化/推理失败回退、共享 OCR 实例、进程内 ROI 缓存、快速/完整测试分层、
可选依赖和机器可读基准均已实现。主环境当前仍只有 `CPUExecutionProvider`，
`auto` 回退 CPU 已验证；隔离的 DirectML Runtime 已验证 `DmlExecutionProvider`
可用，并通过完整真实回放与性能门槛。CUDA 仍需在具备匹配运行库的环境里复验，
不能用 CPU 回退结果代替。

### 里程碑 5：真实环境验收

1. 观察模式完整覆盖一次人工操作链路。
2. 自动模式跑通单角色。
3. 单角色连续成功 3 次。
4. 启用三个角色。
5. 三角色完整流程连续成功 3 次。

## 9. 验收标准

- 真实回放数据集关键状态识别率 100%。
- 高风险动作的误点击为 0。
- 每次点击都有动作结果验证记录。
- 未知过渡帧不会触发点击。
- 窗口尺寸不变时视口参数保持稳定。
- 窗口尺寸变化后能够自动重新校准。
- 失败时同时生成原图、标准化图、标注图、观察 JSON 和日志。
- 单角色和三角色均按上述次数完成真实连续运行。

## 10. 工程约束

- 保留现有用户改动，不回退无关文件。
- 使用 `apply_patch` 进行手工代码编辑。
- 新依赖优先支持中国镜像安装。
- 不把 `runs` 全量加入版本控制，只挑选最小回放样本。
- 回放图片优先压缩，同时确保文字和按钮边缘可识别。
- 每个里程碑完成后运行完整测试，并报告真实测试和尚未验证的部分。
- 不以 `FakeGame` 测试通过代替真实识别验收。
- GPU 加速必须保留 CPU 回退路径，且不得降低识别结果一致性。

## 11. 建议的首个新会话任务

新会话首先只完成里程碑 1，并为里程碑 2 建立接口：

1. 阅读当前 `bot.py` 的截图、标准化、识别和等待实现。
2. 分析最新失败日志和截图。
3. 实现稳定视口校准及缓存。
4. 建立真实截图回放清单和测试器。
5. 验证运行时与离线标准化一致。
6. 为 `Observation` 预留清晰接口，但暂不一次性迁移全部流程。

完成里程碑 1 后，再在同一会话继续里程碑 2，避免大规模重写后无法定位回归来源。
